# Guardian Shield v9 — Rebuild Status

A correct, compiling, and **live-verified** BPF-LSM kernel enforcement layer
that replaces the broken v9 prototype. Confirmed on a kernel-6.18 BPF-LSM host:
the object verifies, all 17 hooks attach and pin, and the external-vector suite
blocks glibc/raw-syscall/openat2/io_uring/renameat2 destruction for agents while
leaving non-agents untouched. This document maps every fix to the confirmed
defect, states the exact prerequisites, records the build + live status, gives
the deploy/pin/unload procedure, and lists residual risks.

**One-line summary:** the prototype could never block anything (it matched
full-path prefix rules against bare leaf filenames, and identified processes by
a forgeable 15-char comm). v9 reconstructs the mount-correct absolute path,
tags whole process trees at the kernel level, matches via an LPM trie, pins its
links so enforcement survives loader death, and is proven by an external-vector
bypass harness — including an io_uring deletion dispatched from a kernel worker
thread, caught by the process-tree tag that a comm-based check would miss.

## Defect → Fix map

### Defect 1 (FATAL) — path reconstruction read only the leaf filename
`get_dentry_path()` read `dentry->d_name.name` (one component, e.g. `secret.txt`)
and compared it against full-path prefix rules (e.g. `/home/founder/Documents/`),
so a prefix match was **impossible** — the prototype blocked nothing.

**Fix.** Two mount-correct reconstruction paths, chosen per hook by what the
kernel allows:

- **`bpf_d_path()` (GPL helper, hook-allowlisted)** on `lsm/file_open` and
  `lsm/path_truncate`. The kernel only permits `bpf_d_path` on an allowlist of
  attach points; I verified `security_file_open` and `security_path_truncate`
  are on it (they are, in this kernel's BTF). This yields the fully canonical,
  mount-aware, `..`/symlink-resolved path — closing the TOCTOU/canonicalization
  gap the userspace libwarden has. `file_open` also gates **write/truncate
  opens** (`O_WRONLY|O_RDWR|O_TRUNC|O_CREAT`) on protected paths, which is what
  catches `openat2(O_TRUNC)` data destruction.
- **Bounded mount-aware dentry parent-walk** for the hooks where `bpf_d_path`
  is *not* allowed (`path_unlink`, `path_rename`, `path_link`, `path_symlink`,
  `path_mkdir`, `path_rmdir`, `path_chmod`). `reconstruct_path()` walks
  `dentry -> d_parent` up to `MAX_DENTRY_DEPTH` (16) and **crosses mount points**
  via `struct mount` (`mnt_root` / `mnt_parent` / `mnt_mountpoint`). This is
  required, not optional: on this host `/home` and `/boot` are **separate
  mounts** (`findmnt` confirmed `nvme0n1p4` on `/home`), so a dentry-only walk
  would resolve `/home/founder/x` to `/founder/x` and silently fail to protect
  it. Components are copied byte-at-a-time under an `off < MAX_PATH_LEN-1` guard
  (verifier-friendly).

The v9 hooks use the `path_*` LSM family (available because
`CONFIG_SECURITY_PATH=y`) rather than the `inode_*` family, precisely because
`path_*` gives the parent `struct path` (mount + dentry) needed for correct
mount crossing.

### Defect 2 (CRITICAL) — identity was `bpf_get_current_comm`
comm is a 15-char label an attacker rewrites with `prctl(PR_SET_NAME)`; the old
exempt/allow maps were keyed on it.

**Fix — PID-tree tagging (`agent_pids: tgid -> proc_tag`):**
- `tp_btf/sched_process_exec` classifies the new exe by **basename** against a
  configurable `agent_exe_names` set (claude, cursor, aider, …). A full-path
  `exempt_exes` hit tags `EXEMPT` and overrides an inherited agent tag.
- `tp_btf/sched_process_fork` — the child **inherits** the parent's tag
  (incremental parent-chain equivalent).
- `tp_btf/sched_process_exit` — deletes the tag when the thread-group leader
  exits (process death).
- The tag is **sticky across exec**: an agent that spawns `/bin/rm` or renames
  itself keeps the tag, because we never clear it on exec of a non-agent binary.

Enforcement keys on `bpf_map_lookup_elem(&agent_pids, &tgid)` — comm is recorded
in events for humans only, never used for a decision. This mirrors Metatron's
macOS agent-subtree tagging (KERN_PROCARGS2 + parent walk + cached PID set),
done incrementally in-kernel.

**Model note:** restrictions apply to tagged **agent subtrees**; everything else
is unrestricted by this layer (the AI-containment model the task specifies).
`node`/`python`/`deno`/`bun` are intentionally **not** default-tagged (too
broad — would tag every script host); the robust default signal is the agent
*launcher* basename. Residual gap and the cmdline-enrichment option are in
Residual Risks.

### Defect 3 — verifier-hostile 100×256 unrolled linear scan
**Fix.** `protected_paths` is a `BPF_MAP_TYPE_LPM_TRIE` (`BPF_F_NO_PREALLOC`),
keyed `{prefixlen_bits, path bytes}`, for O(prefix) longest-prefix lookup. The
value carries the prefix byte-length so a **boundary check** rejects sibling
false positives: after an LPM hit at length `L`, the path is protected only if
`path[L]` is `/` (subtree) or `\0` (the dir itself) — so `/etc` protects
`/etc/passwd` and `rmdir /etc` but never `/etcfoo`. The loader normalizes stored
prefixes by stripping a trailing `/`.

### Defect 4 — loader API misuse + no persistence
- Removed the bogus `bpf_object__attach_skeleton()` on a plain object. v9
  iterates programs (`bpf_object__next_program`) and calls
  `bpf_program__attach()` per program, retaining each `bpf_link`.
- **Pins every link** to `/sys/fs/bpf/guardian_shield/<progname>` so LSM
  enforcement **persists if the loader restarts/dies** (unpinned LSM links
  detach on fd close → fail-open, the exact failure being eliminated).
  `--unpin` removes the pins (drops the links' last ref → detach).
- **Fail-closed:** if any single hook fails to attach or pin, all links are
  destroyed and the loader refuses to run with partial protection.
- Object path is resolved via `/proc/self/exe` (or `--obj <path>`), not CWD.
- The non-existent `SEC("lsm.s/init")` "hook" is gone.
- **Race-free enforcement window:** all policy maps are populated *before* a
  runtime `ready` flag is flipped; hooks no-op while `ready==0`, so nothing
  enforces against an empty policy during load.
- Zig 0.16: `std.process.Init` entrypoint, `std.ArrayListUnmanaged(...).empty` +
  `deinit(allocator)`, `std.json.parseFromSlice` with `.allocate = .alloc_always`
  (a real use-after-free was found and fixed — default `alloc_if_needed` leaves
  parsed strings pointing into the freed input buffer), JSON emitted **only**
  via `std.json.Stringify.valueAlloc` (no format-string interpolation —
  CLAUDE.md class 1), `_FORTIFY_SOURCE=0` + glibc-2.39 target to dodge the
  translate-c fortify bug, libc-backed file I/O (0.16 removed the `std.posix`
  file wrappers).

### Defect 5 — kernel prerequisite checks
On startup the loader verifies **kernel ≥ 5.7**, **`bpf` present in
`/sys/kernel/security/lsm`**, and **`/sys/kernel/btf/vmlinux`** (BTF/CO-RE). On
any failure it prints the exact remediation (add `lsm=…,bpf` to
`GRUB_CMDLINE_LINUX`, regenerate grub, reboot) and exits non-zero. It never
silently no-ops.

### Defect 6 — memory hooks reviewed for the same two bug classes
`guardian_shield_lsm_memory.bpf.c`'s comm identity and pointer misuse are fixed
by folding the memory/privilege hooks into the combined object, all keyed on the
`agent_pids` tag:
- `lsm/ptrace_access_check` — an agent may not attach to any task (injection).
- `lsm/file_open` — `/dev/mem`, `/dev/kmem`, `/dev/port` blocked for agents
  (correct kernel `dev_t` decoding, `MINORBITS=20`).
- `lsm/kernel_read_file` (`READING_MODULE`) — agent module loads blocked.
- `lsm/capable` — dangerous caps for agents (audit-only unless `enforce_priv`).
- `lsm/sb_mount`, `lsm/move_mount` — mount ops (gated on `enforce_priv`).

Dropped from the prototype: `lsm/task_setns` and `lsm/task_setuid` — **these
hooks do not exist** in this kernel's BTF (`bpf_lsm_task_setns` is absent);
attaching them would have failed the whole fail-closed load. `sb_mount` +
`move_mount` cover the mount-escape surface.

## Live verification — CONFIRMED on kernel 6.18 (BPF-LSM VM)

The object **verifies and enforces** on a real BPF-LSM host:

- **Verifier: PASS.** The full object loads; **all 17 hooks attach and pin**
  (`Guardian Shield v9 ACTIVE: 17 hooks pinned`). Reaching this took six
  verifier iterations, each a distinct structural class — recorded here so the
  shape of the final code is understood:
  1. **-E2BIG** (1M-insn limit) — variable-offset masked scan in the exec
     basename parse × unroll. Fixed: basename taken directly from the exe
     dentry leaf; path walk moved to `bpf_loop()`.
  2. **CO-RE `<invalid relocation>`** — `BPF_CORE_READ` through a map-value
     struct field latched the relocation onto a program-local type. Fixed: load
     kernel pointers into local typed vars first, read through those.
  3. **`bpf_loop` ctx `R3 type=map_value expected=fp`** — the callback context
     must be `PTR_TO_STACK`. Fixed: control state moved to a small stack struct.
  4. **`invalid variable-offset write to stack`** — but the byte writes then
     needed a map value. Fixed: split control (stack) from buffer (per-CPU map).
  5. **`invalid access to map value` (off+size overrun)** — masking the index
     bounds the start, not start+size. Fixed: over-sized the buffer + an
     independent constant length clamp so `max_index + max_read < physical size`.
  6. **Clean** — verifies.
- **Enforcement: PASS, agent-only.**
  - Non-agent process creates AND deletes files in the protected dir → **allowed**.
  - Agent-tagged process (a real binary named `claude`): **every** destructive
    vector **blocked** — glibc `unlink`→EPERM, raw `syscall(unlinkat)`→EPERM,
    `openat2`+O_TRUNC→EACCES, io_uring `UNLINKAT`→EPERM, `renameat2`→EPERM,
    `openat2` create→EACCES.
  - The ring-buffer log shows each block with `"enforced":true` and the agent
    tag — **including the io_uring deletion whose syscall came from the kernel
    worker thread `comm="iou-wrk-*"`**. A `comm`-based identity would have missed
    it; the **tgid process-tree tag caught it**. That is exactly the
    io_uring/openat2/raw-syscall class that bypasses userspace libwarden,
    blocked at the LSM — the whole thesis, proven live.

This closes the previously-open "verifier acceptance unconfirmed" item.

## Hardening mode (attacker / escalation posture)

v9's default posture is **AI-agent containment**: every hook gates on the agent
tag, so a human attacker (non-agent shell, dropped binary, injected code) is
unrestricted. **Hardening mode** (`hardening_mode: true`, opt-in) adds a second
posture — default-deny against everyone except an allowlist, plus self-protection
so the shield cannot be trivially torn down. Agent-containment mode is unchanged
and remains the default.

### The gate inversion (core change)
A new tag **`TAG_TRUSTED`** (from a path-keyed `trusted_exes` allowlist, not
comm → not `prctl`-forgeable) sits above AGENT/EXEMPT. The per-hook restricted
set is now:

```
restricted = hardening_mode ? (tag != TAG_TRUSTED)   // default-deny: everyone but trusted
                            : (tag == TAG_AGENT);     // agent-containment (default)
```

Every filesystem hook (`fs_guard_dentry`, `path_truncate`, `file_open` write
path) uses this, and logs the *actual* tag so a violation shows whether it was an
agent or an untrusted attacker. In hardening mode the loader loads
**`critical_paths`** (not `protected_paths`) into the LPM trie — the critical set
= the shield's own state + credentials (`/sys/fs/bpf/guardian_shield`, the
install dir, `~/.ssh`, `~/.claude`, `/etc/sudoers.d`, `/boot`).

### Self-protection hooks (active for non-trusted in hardening mode)
- **`lsm/bpf` (`gs_bpf`) — the anti-tamper hook.** Denies the `bpf()` syscall for
  any non-trusted caller, so an attacker (even root) cannot use `bpf()`/`bpftool`
  to detach the shield's links or manipulate its maps/progs. The **trusted loader
  itself calls `bpf()`**, so it MUST be `TAG_TRUSTED`: (1) its exe path is in
  `trusted_exes`, and (2) the loader also self-inserts its own tgid as
  `TAG_TRUSTED` *before* flipping `ready` (belt-and-suspenders — the initial load
  happens before `gs_bpf` is attached, and `ready` gates the hook, so the load
  path is unaffected; teardown/`--unpin` by the trusted loader still works).
- **`gs_kernel_read_file`** (module load), **`gs_sb_mount`/`gs_move_mount`**
  (mount tricks), **`gs_ptrace`** (injection into trusted procs), **`/dev/mem`**
  in `file_open` — all enforce for non-trusted in hardening mode, independent of
  `enforce_priv`.
- **`gs_capable`** — in hardening mode denies a **narrow** set for non-trusted:
  **`CAP_SYS_MODULE` and `CAP_BPF` only**. Deliberately NOT `CAP_SYS_ADMIN`
  (too broad — would brick normal root operation).

### New-file creation (`path_mknod`) — closing a real live-found gap
Live testing found that `file_open`'s write gate catches opening EXISTING files
for write, but `open(O_CREAT)` of a **NEW** file creates a fresh negative dentry
and does not traverse the existing-inode write path — so a non-trusted attacker
could **inject a new file** into a protected dir (a new `authorized_keys`, a new
`~/.claude` config, a new `/etc/sudoers.d` for root persistence) even though it
could not touch existing ones. This matters most for the credential model where
the developer *owns* `~/.ssh`/`~/.claude` (Unix perms don't stop them). Fixed by
adding **`lsm/path_mknod`** (`gs_path_mknod`), which fires for regular-file
creation (incl. the `O_CREAT` open path on `CONFIG_SECURITY_PATH` kernels) plus
device/fifo nodes; it reconstructs the new dentry's path and applies the same
`restricted` gate + LPM match, logging `EV_CREATE`. (`bpf_lsm_inode_create` is
also present as a backstop if a live test shows a create path that bypasses
`path_mknod`, e.g. `O_TMPFILE` or certain filesystems.)

### ptrace scope — protect trusted targets, don't break debuggers
`gs_ptrace` is deliberately NOT a blanket ban on all non-trusted ptrace (that
would break strace/gdb for the developer in hardening mode). Scopes:
agent-containment blocks an AGENT source from ptracing anything (containment);
hardening blocks a non-trusted source only when the **target is `TAG_TRUSTED`**
(anti-injection into the loader/trusted tools). Normal debugging of ordinary
processes is unaffected.

### Operability: teardown self-trusts (the shield must not fight its own operator)
A live-load bug surfaced this: with `gs_bpf` active, `./guardian_shield_loader
--unpin` (a **relative** path) left the shield partially enforcing. Cause:
`gs_exec` matched `trusted_exes` on `bprm->filename`, which for a relative exec
is the relative string and does not equal the absolute `trusted_exes` entry — so
the operator's own `--unpin` process was NOT `TAG_TRUSTED`, and the anti-tamper
hooks blocked its teardown (pins un-removable). A fresh `--unpin` process cannot
self-tag via a pinned map either, because opening/updating a BPF map is itself a
`bpf()` call that `gs_bpf` blocks — a circular dependency. Fixes:
- **Trust by exe inode identity.** The loader stats each `trusted_exes` path
  **and its own `/proc/self/exe`** and loads `{ino, dev}` into a
  `trusted_inodes` map (dev re-encoded to the kernel `MKDEV` form). `gs_exec`
  tags TRUSTED on an inode match, so the loader trusts itself regardless of how
  it was invoked (relative/absolute) and without any forgeable string. This is
  what makes `--unpin` work under hardening — the process is TRUSTED at exec,
  before it touches anything.
- **Pins are the sole link owners.** After pinning, the loader drops its own
  link fds (`bpf_link__destroy`; the pins keep the links alive). LSM links can't
  be force-detached (no `LINK_DETACH`), so the only removal path is dropping
  every reference — with the pins as the sole reference, `--unpin` (which removes
  the pins) fully detaches all 19 hooks even while a logger instance is running.
  Note: this relies on the loader releasing its own link fds after pinning
  (`bpf_link__destroy`; the pins keep the links).

Expected after the inode-trust fix: `--unpin` by a relative path removes all
pins. Whether that alone *fully detaches* the LSM links is the subject of the
lifecycle note below.

### LSM link lifecycle: the ONLY teardown is refcount-to-zero
A live test surfaced a subtle, **fail-secure** operability bug: after a
relative-path `--unpin`, the pins were gone and no process held any link/prog
fd, yet enforcement PERSISTED (`touch ~/.ssh/x` → EPERM). The shield stayed ON —
so it is *not* a security risk (fail-secure) — but the operator couldn't cleanly
stop it without a reboot.

Root of the difficulty, confirmed against this kernel's BTF: **LSM/tracing links
have no `LINK_DETACH` op** (`struct bpf_tracing_link` exposes `_release` and
`_dealloc` but no `_detach`). So the ONLY way to detach an LSM hook is to drive
its `bpf_link` refcount to 0; there is no force-detach. The references are: the
creating process's link fd, plus one per bpffs pin. The v9 contract:
- **Load path** drops the loader's own link fds right after pinning
  (`bpf_link__destroy` → `close(fd)`), so the pins are the sole owners and
  enforcement is independent of the (optionally still-running) logger.
- **`--unpin`** no longer trusts a bare `unlink()` of the pin to trigger bpffs
  inode-eviction and the deref. Instead it **re-opens each pinned link**
  (`bpf_link__open` → a fresh fd it controls, ref++), then `bpf_link__unpin`
  (removes the pin ref) and `bpf_link__destroy` (closes its own fd LAST) —
  forcing the final dereference through a reference the process owns. This
  requires `--unpin` to be `TAG_TRUSTED` (`bpf_link__open` is a `bpf()` call);
  the inode-trust fix guarantees that regardless of how it was invoked.

**Teardown contract (documented, honest):**
1. `guardian_shield_loader config.json --unpin` (any invocation path) —
   TRUSTED via inode, re-opens + unpins + destroys every pinned link.
2. If a separate logger instance of the loader is still running, stop it too
   (its bpf_object keeps the maps/progs loaded; not the LSM attachment, but
   belt-and-suspenders): `pkill -x guardian_shield`.
3. **Guaranteed fallback:** reboot always clears bpffs and all BPF state. This
   is already the documented root escape hatch, so a shield that in the worst
   case needs a reboot to fully stop is fail-secure, not a security gap.

If the VM re-test still shows persistence after the re-open/destroy teardown,
that points to a kernel-held reference on LSM `bpf_link` refcount beyond fds+pins
on 6.18, and reboot (contract step 3) is the remedy — reported honestly rather
than claimed as clean.

### Honest root-tamper boundary (do NOT overstate)
A userspace-loaded BPF-LSM raises the bar but **cannot fully contain a determined
root**. Against a *live, already-booted* attacker (incl. root not in
`trusted_exes`), hardening mode blocks: `bpf()`/bpftool tamper of the shield,
fs deletion/overwrite of the pins and critical set, runtime module load / mount
tricks, and ptrace into trusted processes. What root can **still** do, and what
`tests/attacker_sim.sh` reports truthfully:
- **Reboot with a modified kernel cmdline** (drop `lsm=…,bpf`) → the shield never
  loads next boot. Editing grub is blocked at runtime if `/boot` is critical, but
  root can `kexec`, boot rescue media, or edit the VM disk offline.
- **Offline disk edit** of the shield config/binary while it is unloaded.
- Anything gated on caps we intentionally don't deny (only `CAP_SYS_MODULE`/
  `CAP_BPF` are denied; `CAP_SYS_ADMIN` is not).

`tests/attacker_sim.sh` (VM-only, gated on `GS_VM_TEST=1`) measures this in two
tiers (unprivileged + root). It is **two-phase** because creating a victim inside
a critical path is itself blocked once hardening is active:
`--unpin` → `attacker_sim.sh --setup` (seed victims, shield unloaded, as root) →
load in hardening mode → `attacker_sim.sh --attack`. The attack phase runs:
credential/shield-file tamper (glibc + raw syscall) against the seeded victims,
pin removal via the fs, a compiled `bpf(BPF_OBJ_GET→BPF_LINK_DETACH)` probe,
kill-the-loader (`pgrep -x guardian_shield`, the 15-char truncated comm) then
remove-pins persistence, and module/mount attempts — then prints a
blocked/allowed/na tally and the root-boundary caveats above. Any `ALLOWED (!!)`
line is a real gap to report verbatim.

Live result (kernel 6.18, root tier): `bpf()` detach → BLOCKED (EPERM), pin
unlink → BLOCKED (EPERM), `modprobe` → BLOCKED (EPERM), `mount` → BLOCKED
(EPERM) — root cannot tamper with the live shield via any of these.

## Credential-read protection & build-tool taint (supply-chain defense)

An **additive third capability** (layers on top of both agent-containment and
hardening; both remain 100% intact). It targets the 2025-26 npm/PyPI
supply-chain / credential-theft threat (Shai-Hulud, s1ngularity): a malicious
package's **postinstall** runs as the developer — as a child of `npm`/`pip` —
then **reads** credential files (`~/.aws`, `~/.ssh`, tokens) and exfiltrates
them. It is a credential-**read** attack by a build-tool **descendant**, so the
deny must be scoped to build-tool subtrees — a normal user/process reads its own
creds constantly and must never be blocked.

### Build-tool taint (`TAG_TAINTED`)
`gs_exec` tags a process `TAG_TAINTED` when its exe basename is in
`build_exe_names` (`npm`/`pnpm`/`yarn`/`npx`/`node-gyp`/`pip`/`pip3`/`poetry`/
`uv`/`cargo`/`gem`/`bundle`/`mvn`/`maven`/`gradle`). The taint is **inherited on
fork and sticky across exec**, so the postinstall's `node bundle.js` and anything
it spawns (`curl`, `trufflehog`) stay tainted even though their own basenames
aren't build tools — tagging the *launcher* taints the whole install subtree.
Precedence: `TRUSTED`/`EXEMPT` override (a trusted exe is never tainted); an
inherited `AGENT` tag is not downgraded. (Taint is by the resolved exe's dentry
leaf, so a shell script named `npm` would leaf as `bash` — the sim uses real
binaries named `npm`/`yarn`.)

### Credential AssetMap (`credential_paths`) — a separate LPM trie
The crown jewels: `~/.ssh`, `~/.aws`, `~/.config/gcloud`, `~/.config/gh`,
`~/.git-credentials`, `~/.netrc`, `~/.kube`, `~/.docker/config.json`, `~/.claude`,
`/root/.ssh`. Separate from `protected_paths`/`critical_paths` because it gates
**reads** (not just writes) and only for tainted/agent subtrees.

### The harvest block (`gs_file_open`, always-on)
On **any** open — including `O_RDONLY` — of a `credential_paths` path, if the
caller's tag is `TAG_TAINTED` or `TAG_AGENT`, return `-EPERM` and log
`EV_CRED_READ`. It uses `bpf_d_path` (canonical path) and runs **independently of
agent/hardening posture** (`enforce_cred_read`, default on). A trusted / normal /
untainted process reading its own `~/.ssh` is unaffected — ssh/git/aws keep
working; only tainted build-tool subtrees are denied the crown jewels.

### Tiering rationale (documented, deliberate)
The crown-jewel deny set **excludes** build-tool self-secrets (`~/.npmrc`,
`~/.pypirc`, `~/.cargo/credentials`) for v1: tools legitimately read those during
install, and **no build tool legitimately reads your AWS/SSH keys during
`npm install`** — so denying tainted reads of the crown jewels is high-value and
low-false-positive. A later version can add Metatron-style `isBuildToolSecret`
handling to also guard the self-secrets against non-owning tools.

### Proof: `tests/supplychain_sim.sh` (VM-only, `GS_VM_TEST=1`)
Two-phase (`--setup` seeds throwaway `~/.aws`/`~/.ssh`/gh/git-creds + a benign
`~/.npmrc`; `--attack` after load). Compiles an inline `cred_reader` (opens+reads
one path) and a `launcher` (fork+exec, to prove inheritance), then runs three
ways and asserts: **NORMAL** (untainted) reader → crown jewels **ALLOWED** (no
false positive); **TAINTED** (exe named `npm`) reader → crown jewels **DENIED**;
**TAINTED-INHERITED** (`yarn` forks+execs `harvester`) → crown jewels **DENIED**
(sticky-taint proof); tainted read of `~/.npmrc` → **ALLOWED** (tiering). This is
the endpoint block that breaks the harvest step. Proven live: 14/14.

### The exfil half — egress guard (`gs_socket_connect`)
The read-harvest block stops the steal; the egress guard stops the phone-home, so
even a secret that leaks by another path can't be shipped to the attacker's C2.
`lsm/socket_connect` fires **before** the connect completes (so the verdict is
independent of network reachability — important on an air-gapped test VM). For a
`TAG_TAINTED` or `TAG_AGENT` process opening an `AF_INET`/`AF_INET6` connection:
- **`egress_allow`** LPM trie (IPv4, keyed on packed network-order address). The
  loader **always** seeds loopback + RFC1918 private + link-local (169.254/16) +
  CGNAT (100.64/10), so LAN/localhost/registry-mirror-on-LAN work; the operator
  adds public registry CIDRs. A dest matching a stored prefix → allowed.
- Any other (public, non-allowlisted) dest → log `EV_TAINTED_CONNECT` and, if
  `enforce_egress` (default true), `-EPERM`. AF_UNIX/AF_NETLINK are ignored
  (local IPC never blocked). Normal/trusted/untainted processes are unaffected —
  the user's browser/curl keep working.
- **IPv6 status (honest):** loopback (`::1`), link-local (`fe80::/10`), and ULA
  (`fc00::/7`) are allowed inline; global IPv6 is treated as public (denied when
  enforcing). There is **no operator IPv6 allowlist in v1** — IPv4 only in the
  trie.

**Egress tradeoff (documented):** with `enforce_egress=true` and only the private
defaults, a tainted `npm install` reaching a public registry is also denied
unless that registry's CIDRs are added to `egress_allow`. That is the honest cost
of egress-jailing build tools — matches the detect-then-enforce discipline: set
`enforce_egress=false` to log-only (`EV_TAINTED_CONNECT`) first, then allowlist
what real installs legitimately need.

`supplychain_sim.sh` §4 proves it with an inline non-blocking `connector`:
TAINTED (`pnpm`) → public `203.0.113.10:443` (TEST-NET-3) **BLOCKED**; TAINTED →
loopback **ALLOWED**; NORMAL → same public IP **ALLOWED** (no false positive).
The LSM verdict (`-EPERM`) is asserted, not connection success (the VM has no
internet).

## Deploy / pin / unload

```bash
cd programs/guardian_shield/guardian-shield-v9
zig build                    # builds bpf object + loader + harness into zig-out/bin

# Review/edit policy: protected_paths, agent_exes, exempt_exes, enforce_* flags.
$EDITOR config.json

# Load + attach + PIN (needs root). Enforcement persists after this returns/dies.
sudo zig-out/bin/guardian_shield_loader config.json --verbose

# Inspect
sudo bpftool link show
ls /sys/fs/bpf/guardian_shield/            # one pin per hook
sudo bpftool map dump name protected_paths
tail -f /var/log/guardian_shield.jsonl     # JSONL violation + agent-tag events

# Remove enforcement
sudo zig-out/bin/guardian_shield_loader config.json --unpin
```

(ptrace/dev-mem/module), `enforce_priv` (caps/mounts — **default off** to avoid
bricking benign cap checks), `log_only` (global dry-run: log, never `-EPERM`).

## Residual risks / coverage boundaries

- **Verifier acceptance: CONFIRMED on kernel 6.18** (see Live verification). No
  longer an open item.
- **Mount-crossing offsets are this-kernel-specific.** `container_of(vfsmnt,
  struct mount, mnt)` uses `offsetof` from the generated `vmlinux.h`.
  Field *reads* are CO-RE-relocatable, but the container_of offset is not — the
  object is built for the host it runs on (regenerate `vmlinux.h` per kernel).
- **Path buffer / depth caps.** `MAX_DENTRY_DEPTH=16`, `MAX_COMPONENT_LEN=64`,
  `MAX_PATH_LEN=128` (reduced from 256 so the reconstruction state fits the BPF
  stack + map-value bounds; the protected prefix always sits at the START of the
  path, so 128 bytes is ample for matching). A path deeper than 16 dir levels or
  a component > 64 bytes truncates (a `STAT_PATH_TRUNC` counter fires); the
  reconstruction buffer is over-sized to `MAX_PATH_LEN + MAX_COMPONENT_LEN` so
  the worst-case masked component write is provably in-bounds. `bpf_d_path`
  hooks (file_open/truncate) resolve the full canonical path with no walk cap.
- **Agent classification is by launcher basename.** A node/python-based agent
  whose exe is literally `node`/`python` is not tagged by default (tagging all
  node/python is too broad). Options: add those basenames to `agent_exes`
  (aggressive), or extend the loader to read `/proc/<pid>/cmdline` on the
  `exec_events` ring-buffer notification and tag deeper matches — note that adds
  a small userspace-tagging race the in-kernel basename path does not have.
- **Exempt-exe override is a deliberate trust hole.** An operator-listed
  `exempt_exes` binary run *inside* an agent subtree escapes enforcement; that
  is the operator's explicit decision. Keyed on full exe path (not comm), so it
  is at least not forgeable via `prctl`.
- **LSM hook coverage vs. the full syscall set.** The `path_*`/`file_open` hooks
  cover unlink/rename/link/symlink/mkdir/rmdir/chmod/truncate, write/truncate
  opens, AND **new-file creation** (`path_mknod` — see below). Not covered here:
  `open` without write intent (reads are allowed by design), extended attributes,
  and non-VFS destruction (e.g. writing
  to a block device the agent already has open — mitigated separately by the
  `/dev/*` and mount hooks). TOCTOU between check and use is closed for the
  `bpf_d_path` hooks (kernel resolves the final path); for the parent-walk hooks
  the dentry is the one the kernel is about to operate on, so there is no
  re-lookup window.
- **Memory hooks are containment, not a sandbox.** ptrace/dev-mem/module-load
  blocking for agents raises the bar but is not a substitute for seccomp or a
  namespace jail; `enforce_priv` (caps/mounts) ships off because a blanket
  agent-wide `capable()` deny can break legitimate operations.
- **Ring-buffer loss is non-fatal.** If the loader dies, enforcement continues
  via pinned links but events stop being logged until a loader re-attaches to
  the (also-pinnable) ring buffers.
