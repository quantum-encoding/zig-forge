# Review — September 2026 (library 1.1.0 → 1.2.0)

What an independent pass found by *running* the code, what was changed, and what is still true
afterwards. Reproduce everything with:

```bash
zig build test -Dtarget=x86_64-linux-musl     # 228 tests, incl. the differential suite
zig build ct-check                            # constant-time guard (python3)
cd quantum-vault-sys && cargo test            # after `zig build -Doptimize=ReleaseSafe`
```

## 1. The cryptography is correct

Driven with the same seeds as Zig's independent `std.crypto` implementations:

| Check | Result |
|---|---|
| ML-KEM-768 keys, ciphertexts, shared secrets, cross-decapsulation, implicit-rejection secret | byte-identical on every seed |
| ML-DSA-65 key pairs | byte-identical on every seed |
| ML-DSA-65 signing core | byte-identical once the message framing matches |
| Verifier strictness: single-bit mutations, half aimed at the hint encoding | identical verdict on all of them, none accepted |

This is now a permanent test (`src/differential_std.zig`).

## 2. Findings and fixes

### 2.1 Signatures did not interoperate — fixed by adding the standard interface
`sign` is FIPS 204 `ML-DSA.Sign_internal` (`μ = H(tr ‖ M)`). Everyone else implements
`ML-DSA.Sign` (`μ = H(tr ‖ 0x00 ‖ len(ctx) ‖ ctx ‖ M)`). Measured: **0 of 40** signatures were
accepted by a standard verifier. Added `signWithContext` / `verifyWithContext`,
`qv_mldsa65_sign_v2` / `qv_mldsa65_verify_v2`, Rust `sign_with_context` /
`verify_with_context`, and Worker `mlDsaSignWithContext` / `mlDsaVerifyWithContext`. v1 is
unchanged byte-for-byte (the ACVP KATs still pass) so existing signatures keep verifying. The two
framings never cross-verify.

### 2.2 Division on secret data (KyberSlash class) — fixed and guarded
`compressMessage` was `((2x + q/2) / q) & 1` on the decrypted message — the expression
KyberSlash1 attacked in the reference code — `compress` divided by `q`, and both NTTs reduced
with `@mod`. Whether that is a multiply is the compiler's decision. Divide instructions inside
cryptographic functions, before → after:

| Build | Before | After |
|---|---|---|
| wasm32 ReleaseSmall (**what `zig build wasm` ships**) | 15 | 0 |
| wasm32 ReleaseFast | 108 | 0 |
| aarch64-macos ReleaseSmall | 11 | 0 |
| x86-64 / aarch64 ReleaseSafe and ReleaseFast (what `zig build cross` ships) | 0 | 0 |
| Debug (the default for a bare `zig build`) | 40 (ML-KEM alone) | not checked — never ship Debug |

Replaced with `ml_kem.modQ`, a reciprocal multiply in `compress`, and in ML-DSA a fold-and-Barrett
`modReduce` valid for every `i64` (the lazy inverse NTT really does produce ~2^54 inputs), the
reference's shift-based `decompose`, and masked `power2Round` / `centerReduce` / `checkNorm`.
Every replacement is tested exhaustively against its definition — all 67 million inputs of `modQ`,
every coefficient and `d` for `compress`, all 8,380,417 residues for `decompose`, `power2Round`
and `centerReduce` — and the byte-exact KATs are unchanged. `zig build ct-check` fails the build
if a divide returns; pointed at the old listings it flags all of the above.

Exploitability of the wasm32 case in a Worker was not measured. The fix costs nothing, so it was
not worth finding out.

### 2.3 Missing input validation — fixed
- `decaps768` did no FIPS 203 §7.3 decapsulation-key check. A corrupt key silently yields a wrong
  secret for every ciphertext. Added `validateDecapsulationKey768` / `decaps768Checked`; the C ABI
  and hybrid ABI now check on every call. `decaps768` keeps its signature for Zig callers that
  validate once at import.
- `encapsInternal768` is `pub` and skipped the §7.2 modulus check. It now performs it.

### 2.4 Found on the way
- **Static archives did not link from C or Rust on x86-64 Linux** (`__zig_probe_stack`
  undefined): compiler-rt was not bundled. Already broken at `d3c6bb7`. Fixed.
- **`ml_kem.montgomeryReduce` was wrong** — negated inverse constant and an overflowing multiply.
  Nothing called it, so no output was affected. Corrected and tested.

## 3. Still true — limitations that remain

- **Scope.** One parameter set each (ML-KEM-768, ML-DSA-65). No HashML-DSA. No AEAD and no
  Ed25519 here. A KEM authenticates nobody: the application must sign.
- **Hybrid v2 is not X-Wing.** Same binding order, but HKDF-SHA3-256 rather than X-Wing's single
  SHA3-256 with its label, so it does not interoperate with X-Wing implementations.
- **Stack.** ML-DSA signing has a single ~126 KiB frame (verify ~80, keygen ~77, ML-KEM decaps
  ~23). musl's default thread stack is 128 KiB: sign on the main thread or size the stack.
- **Worker glue allocator.** `worker/quantum-vault.js` writes caller buffers at a fixed 64 KiB
  offset into linear memory, which is the bottom of the module's 1 MiB stack region. It works
  because the stack grows down from the top and never gets that deep; it is not a real allocator.
- **Assurance.** A handful of ACVP anchors plus the differential suite; no ctgrind / dudect; no
  third-party audit; not CAVP/FIPS 140-3 validated, so "FIPS 203/204" here means "implements",
  not "validated". No licence file.
- **Build environment.** Zig 0.16.0 exactly. On current Arch Linux the native test executables do
  not link (`.sframe` relocations in glibc's `crt1.o`), and `tools/secrets.zig` fails its C import
  against glibc's fortified `fcntl2.h`; both are host/toolchain issues, not library bugs.
- **Strategy.** Zig's standard library now ships ML-KEM and ML-DSA. What this project uniquely
  provides is the C ABI, the hybrid combiner, the Rust crate and the packaging.
